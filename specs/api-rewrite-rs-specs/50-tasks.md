* **T61 Concurrency & pool tuning: deadlock retry, `READ COMMITTED`, pool sizing.** (`54` B10.) The move transaction (`cards/routes.rs::move_card`) already retries a **same-card race** (bounded 5×) but NOT a MySQL **deadlock** (`1213`) or **lock-wait timeout** (`1205`), which the `SELECT … FOR UPDATE` + range-`UPDATE` pattern can produce under concurrent cross-column moves (the stable ascending lock order makes deadlock unlikely, not impossible). Extend the bounded retry to cover `1213`/`1205`, with the same bounded attempt count + a small backoff, and a test that proves the retry path is **taken** (not merely present). **Three implementation details (verified 2026-10-22 against the MySQL 8.4 reference manual):** (1) **match the error NUMBER, not the SQLSTATE** — `1213` is SQLSTATE `40001` but `1205` is SQLSTATE `HY000`, so a `40001`-only matcher silently misses every lock-wait timeout; (2) `1213` rolls back the **whole** transaction but `1205` rolls back **only the current statement** by default (the tx survives half-applied), so the retry must **explicitly `ROLLBACK` the whole transaction** rather than assume it is already dead; (3) `1205` is rarely observed end-to-end — `innodb_lock_wait_timeout` defaults to 50 s but the app's `TimeoutLayer` is 30 s, so the request aborts first; handle it anyway (both are tunable) but do not over-invest.
