# Lessons learned — CI & code quality (backend-rs)

Source: extracted from root `AGENTS.md` (2026-11-10).

### Code review + quality baseline (2026-10-22, `backend-rs/`)

A review of `backend-rs/` (organization, architecture, idiomatic Rust, industry best practices) produced a 10-axis scorecard and a 9-task program (`specs/api-rewrite-rs-specs/54-rust-idiom-hardening.md` + `50-tasks.md` Phase 7, T54–T62) to lift every axis to ≥ 9.5/10. Lessons:

- **A gate that has never executed is not a gate.** `backend-rs/.github/workflows/ci.yml` sat one directory deep — GitHub discovers workflows ONLY at the repo root's `.github/workflows/` — so the pipeline had **never run**. Replaying its grep gate by hand immediately failed on three `expect` sites. A perfect gate definition is worth less than a green run: **validate every gate by making it go red on purpose**, and check the workflow's LOCATION, not just its content.
- **A hand-maintained allowlist drifts — assert it with a test.** `CorsLayer::allow_methods` omitted `PUT`, so `PUT /cards/{id}/labels/{label_id}` was blocked by the browser preflight while every other verb worked (the frontend calls it; compose sets `VITE_API_URL`, making the call cross-origin). The fix is the method list AND a preflight test that asserts every served verb survives — axum does not expose the route table, so the test is the guard. **Landed in T55.**
- **A test that asserts the MECHANISM is not a test of the POLICY.** The pre-existing `health::cors_preflight_matrix` checked ACAO + credentials for **POST only** — correct, green, and blind to the `PUT` drift. The new guard enumerates **every served verb**. A policy test must cover the policy's *domain*, not one sample of it.
- **A gate that has never executed fails on false positives first.** The `no format! in store.rs` gate had never run either, and it failed on the current tree for two reasons that were the GATE's fault: a doc comment merely mentioning `format!`, and `notes::escape_like_pattern` building a **bound value** (the sanctioned LIKE pattern) rather than SQL. **When a gate's intent is right but its matcher is wrong, fix the GATE — and never "fix" the code to satisfy a matcher that misreads the intent.** The gate now skips comments and flags a `format!` only when the built text carries a SQL keyword.
- **A guard that lands red is not a guard.** The CORS preflight guard could not be green until `PUT` was in `allow_methods`, so the fix moved from T56 into T55 (with the guard) rather than landing a red suite in the freshly-activated CI.
- **`#[tracing::instrument(skip(state))]` records the request body.** `skip` takes *only* what it names; every other argument is recorded via its `Debug` impl — so `auth.email` and the DTO body (card `title`/`description`) landed in the span. Skip the body + session explicitly, and gate it with a grep.
- **Make a compile-time fact a compile-time fact.** `to_response(Vec::from([row]), …).pop().expect(…)` asserted a cardinality the compiler already knew. Give the store a single-row constructor (`to_response_one`) so the invariant is structural. **Landed in T55** — `columns/store.rs::to_response_one` + the create/update call sites.
- **A rename must not fail open.** `APP_ENV` defaults to `development`; if `NODE_ENV` were merely ignored, a stale deployment would silently drop `Secure` cookies + `__Host-` + HSTS + deny-all CORS. Boot **fails** when `NODE_ENV` is present — **landed in T54** (`ConfigError::LegacyNodeEnv`, checked *before* `envy` reads `APP_ENV`). Same discipline as the DB-name screen, the charset requirement, the `HASH_COST` prod floor.
- **`common/` is the shared kernel — "features never import each other's STORES" is a SQL-ownership rule, not a ban on sharing a formatter.** `format_timestamp` was duplicated 9× and `common/ownership.rs` was an empty stub while the ownership SQL was duplicated across features. Both belong in `common/`.
- **The rewrite's own constitution is a checklist.** `00-overview.md` says "no NestJS-isms are carried over" — yet `NODE_ENV` and `connect.sid` (express-session's default, copied from `backend/src/main.ts`) survived. Audit the *names* against the constitution, not just the shapes.
- **A lint gate must not flag the fix the same task prescribes (2026-10-22 (c)).** B2's new grep gate was drafted to match `panic!`/`unwrap_or_else`/`todo!`/`unimplemented!` — but `unwrap_or_else` is used **benignly 6×** (it is not a panic spelling) and `state.rs`'s documented fail-fast **is** `unwrap_or_else(|_| panic!(…))`, i.e. the exact line B2 told the executor to write. The gate now matches `panic!`/`todo!`/`unimplemented!` with the ONE boot-time fail-fast explicitly allow-listed. **Rule: before adding a grep gate, grep the tree for the pattern you are about to forbid — and prove the gate goes RED on a probe.**
- **Measure a lint's debt before you make it a gate (2026-10-22 (c)).** `clippy::pedantic` was assumed clean; measured, it is **~370 warnings** (173 `missing_errors_doc`, 45 `must_use_candidate`, 22 `doc_markdown`, ~40 `cast_*`). With CI's `-D warnings` it would have turned a build task into a 370-warning refactor whose `cast_*` fixes change runtime semantics. By contrast `missing_docs`/`unreachable_pub` measured **0** — the deny-level `missing_docs` gate is free. **A lint you have never run is a lint of unknown size.**
- **Two gates over the same subject with different policies guarantee one is red (2026-10-22 (e)).** The workflow ran `cargo audit` AND `cargo deny check advisories` — but `cargo-audit` reads `.cargo/audit.toml` (absent) and `cargo-deny` reads `deny.toml` (4 task-bound ignores). The audit step failed on exactly the advisories the project had deliberately accepted (`error: 4 vulnerabilities found!`). **One policy, one gate, one source of truth** — a second ignore list can only drift.
- **A pipeline that has never run is not a pipeline (2026-10-22 (e)).** T55 moved the workflow to the repo root, which made it discoverable — and therefore verifiable — for the first time. Replaying every step by hand found **two steps RED on every run** (the audit conflict; a SHOW CREATE TABLE assert querying the pre-2026-10-19 `tower_sessions` schema, which the app-database store change had made non-existent). Both had been broken since the day they were written. **Replay EVERY step, not just the ones you changed** — and a step whose assertion describes a schema/table that a *previous* task moved is a step that has been lying since that task.
- **A config file's format belongs to a pinned tool version (2026-10-22 (e)).** `cargo-deny` was installed unpinned; the first run of the T57 policy failed with `unexpected-keys … deny-multiple-versions` because the file was written against a wrong schema. A `deny.toml` is schema-version-sensitive exactly like a `.sqlx/` cache is driver-version-sensitive: **pin the tool** (`--version 0.20.2`) so a tool release cannot turn a dependency bump red.
- **A plan that is EXECUTED drifts from the plan that was READ (2026-10-22 (e)).** Five tasks landed between writing `54` and reviewing it, and in that time the spec had drifted in **both** directions: it still described a tree that no longer existed (`NODE_ENV`, `connect.sid`, the undiscoverable workflow, a failing lint gate, a missing `PUT`) **and** it described a tree that never existed (T65's "five store files" — there are **eight**; "no task touches `openapi.json`" — T57 did). **Re-verify the plan's claims against the tree after every task lands** — and check the plan's *file lists* and *counts*, not just its decisions: a count that is wrong by three makes a task's own acceptance criterion fail.
- **A transitive FEATURE can vanish with the crate that enabled it (2026-10-22 (f)).** The session sweeper's loop (`ExpiredDeletion::continuously_delete_expired`) lives behind `tower-sessions-core`'s `deletion-task` feature — which `tower-sessions-sqlx-store` enabled **transitively**. Dropping the store dropped the feature, and `main.rs` stopped compiling with a method that no longer existed. **When you remove a dependency, enumerate what it enabled transitively**: features, macro exports, and provided trait methods. The fix was to declare `tower-sessions-core` directly with the feature (the SAME version the middleware pins — so no second core in the tree).
- **A dependency's removal can make an invariant STRUCTURAL (2026-10-22 (f)).** The old session store interpolated a **schema name** into every statement, so "the store must live in the pool's database" had to be *configured* (a name, validated at boot, with a `panic!` when it was not a valid identifier). The in-tree store takes the pool and interpolates **nothing** — the same invariant now holds by construction, so the validation, the panic, its `# Panics` contract, and the CI grep gate's allow-list entry for it all became obsolete. **When a gate's allow-list entry loses its subject, delete the entry** — an allow-list entry that outlives its reason is a hole.
- **A dependency major can move a TYPE across a crate boundary (2026-10-22 (g)).** argon2 0.6 / password-hash 0.6 moved the PHC types into a new `phc` crate and changed the trait shape: the salt is now generated internally (`SaltString` is gone) and the verifier takes the PHC **string** (`PasswordVerifier<str>`) instead of a parsed `PasswordHash`. The *output format* was unchanged (the existing test pinned `$argon2id$v=19$m=19456,t=1,p=1$` and kept passing) — **the PHC string is the contract, not the Rust types.** Read the new trait's signature before assuming the changelog's method names: the spec's `hash_password` → `hash_password_into` was wrong for the PHC-string path.
- **A generated type is the CONTRACT — fix the hand-written code, not the generator (2026-10-22 (g)).** The frontend does not type-check against the generated `schema.d.ts` (15 errors; `npm run build` fails). The generator was right and the frontend was wrong: it kept Nest-era **camelCase** names (`boardCount`) against a **snake_case** API, and its hand-written type surgery (`Omit<CardSummary, …> & {…}`) dropped a field's nullability. **When a generated type and hand-written code disagree, the generated type is the contract** — and the error count before/after a regeneration is the cheapest possible way to prove which side moved.
- **"The feature is opt-in, so the file is inert" is a GUESS about a compiler's behaviour (2026-10-22 (h)).** sqlx 0.9's macros **hard-error** when a `sqlx.toml` exists and the `sqlx-toml` feature is off — the plan assumed the file would be ignored. The file was deleted instead (its only setting, `database-url-var = "DATABASE_URL"`, **is** 0.9's default, so nothing changed) rather than the feature enabled. **Read the compiler's error, do not reason about what an opt-in feature "probably" does.**
- **A driver major can change a FEATURE's default (2026-10-22 (h)).** sqlx 0.9 sends only `SET NAMES utf8mb4` and lets the SERVER pick the collation — MySQL 8's default is `utf8mb4_0900_ai_ci`, a **different** collation from this schema's `utf8mb4_unicode_ci`, so the driver version alone would have silently changed the connection's collation. The fix is a **pin in the URL** (`collation=utf8mb4_unicode_ci`), **enforced at boot** (`Settings::validate` rejects a URL without it) and **asserted by a test** (`@@collation_connection`) — because a pin nobody checks is a comment. Note the derived URL matters too: `compose.yaml` passes only the `DB_*` parts, so the pin has to be in the DERIVATION.
- **An advisory with NO patched version cannot be "fixed by an upgrade" (2026-10-22 (h)).** The plan assumed `rsa 0.10.0-rc` would be outside RUSTSEC-2023-0071's range, so the ignore could be deleted with the sqlx 0.9 bump. It is not: the advisory covers **every** `rsa` release and cargo-deny says *"No safe upgrade is available!"*. The ignore stays — with its reason rewritten to state the ACTUAL exposure (`rsa` reaches the tree only via sqlx-mysql's `caching_sha2_password` handshake, whose RSA exchange happens only on a PLAINTEXT connection; production is TLS) rather than a version hope.
- **A toolchain pin CI ignores is not a pin (2026-10-22 (c)).** `dtolnay/rust-toolchain@stable` exports `RUSTUP_TOOLCHAIN`, which **overrides `rust-toolchain.toml`** — so the file can pin 1.99.1 while CI still floats on `stable`. Check the *precedence*, not just the file's existence.
- **Edition 2024 makes `std::env::set_var`/`remove_var` UNSAFE — a test harness that mutates the process env is a blocker, not a detail (2026-10-22 (d)).** The config tests drove `Settings::load_from_env()` by mutating the process env; edition 2024 + `unsafe_code = "forbid"` makes that impossible. The fix is a **seam, not an `unsafe` block**: `Settings::from_pairs(&[(k, v)])` loads from an explicit map (same deserialize + validate path, different source). The tests then need neither `unsafe` nor the `ENV_LOCK` mutex — and become parallel-safe. **When a language edition changes a safety rule, re-check every place that relied on the old rule — the compiler tells you, but only after you try.**
- **A dependency refresh is a security fix — review the lock diff for DOWNGRADES, not just for changes (2026-10-22 (d)).** `cargo deny check advisories` found 6 real advisories; the fix was a `cargo update` that moved **25 crates upward** (incl. `rustls 0.23.45 → 0.23.46`). The review question is "did anything get WORSE?", not "did anything change?".
- **A dead direct dependency can carry a whole second framework (2026-10-22 (d)).** `axum-valid 0.20` had **zero** references in `src/` — and dragged a complete second **axum 0.7.9** (axum-core 0.4.5, matchit 0.7.3), the `validator` 0.18 framework (via `axum-valid`'s DEFAULT features) and a second `garde` 0.20 into the tree beside the real axum 0.8.9. `cargo clippy` never reports an unused *direct* dependency and `cargo build` never reports a duplicate one. **Grep every direct dep against `src/`+`tests/` with a qualified-path pattern** (`tower_http` ≠ `tower`, `std::time` ≠ the `time` crate — that false positive flagged `time` as dead, and it is REQUIRED by `tower_sessions::Expiry`).
- **Bind every supply-chain ignore to a task that removes it (2026-10-22 (d)).** All 6 advisories were removable by later tasks in the same phase (T63/T66/T67). Each `deny.toml` ignore records the advisory id, WHY it is acceptable now, and the exact task that must delete it — an unbound ignore is a silent hole in the gate.
- **The offline-cache tool version must move with the driver (2026-10-22 (c)).** CI pinned `sqlx-cli 0.8.6`; under sqlx 0.9 a 0.8.6 CLI cannot regenerate or validate the `.sqlx/` cache. The CLI pin and the driver pin are one decision — in the manifest, in the workflow, and in the spec's toolchain note.

- Backend shared list-enrichment (`has_description`, `checklist_progress`, card summary select) lives in `backend/src/common/card-summary.helpers.ts` as pure functions taking `Repository<Card>`. Don't reintroduce per-service copies in `cards.service.ts` / `columns.service.ts`.
- Don't place shared helpers inside `cards/` or `columns/` feature folders — cross-feature imports risk circular deps (`arch-avoid-circular-deps`). Use neutral `src/common/`.


## T62 lessons (2026-10-27) — gate execution & Docker build

## T62 lesson (2026-10-27) — a gate's final commit must re-run the gate

**The fmt red (commit `a34eae4c`) came from a task (T61) whose final commit had never executed it.** T61's `cards_move.rs` fault-injection helpers (`AssertSqlSafe` for sqlx 0.9) were committed unformatted; CI run `39962708284` died at step 1 on exactly those 3 diffs; the fix was `cargo fmt`, then `git commit` with the SAME message structure (`T62: cargo fmt on T61's AssertSqlSafe ...`). **Rule:** a gate that has never been executed against the tree is not a gate — it is a definition of what SHOULD fail. Make it fail on purpose (inject the drift, then revert) before adding it to CI.

**The sqlx `prepare --check` red (run `40407062803`, fixed `efb7bf52`) was also a "first execution" failure:** the gate had never run on CI because the pipeline had never passed fmt/clippy. The root cause was the **DB-binding trap** — sqlx 0.9 binds `.sqlx/` query files to DB-qualified names (`kanpad.checklists` vs `kanpad_ci.checklists`); the committed cache is `kanpad.` (dev/test DB), but CI's service DB is `kanpad_ci.`. Without `SQLX_OFFLINE=true`, `prepare --check` reads the live DB, regenerates the `kanpad_ci.`-named cache, then fails it against the committed `kanpad.` files. The fix (`SQLX_OFFLINE=true` env on the step) restores the gate's original intent ("does the committed `.sqlx/` match the committed SQL?") instead of turning it into a DB-name equality test. A gate that depends on the environment of the server running it, rather than the contents of the repo, is a broken gate.

## T62 lesson (2026-10-27, docker build) — `SQLX_OFFLINE` is not cargo `--offline`

**A contract gate can ASSERT the bug.** The `docker-e2e` contract step ran `grep -q -- '--locked --offline' Dockerfile`, i.e. it *required* the exact flag combination that can never work, and it passed — so the gate "verified" a broken contract while the build behind it failed for the first time ever (CI run `40425148777`: `error: no matching package named 'anyhow' found` / `location searched: crates.io index` / exit 101 at `Dockerfile:46`). **When a gate passes and the step it guards fails, suspect the gate's ASSERTION before the code.** Re-aim it, then prove it goes red on a deliberate drift (a Dockerfile copy with `--offline` reinstated).

**`--offline` requires a pre-populated registry; a committed `Cargo.lock` is not one.** A fresh `rust:*` builder ships `CARGO_HOME=/usr/local/cargo` with an EMPTY `registry/` (verified from the image's OCI config blob), so offline cargo fails at dependency **resolution**, before compiling anything — `cargo metadata --offline --locked` with an empty `CARGO_HOME` reproduces it on the host in 0.1 s (`rust-lang/cargo#7085` scenario 1; `#10352`). The fix is `cargo build --locked` with the network ON: reproducibility comes from the lockfile's per-crate checksums + digest-pinned bases, not from cutting the network. Docker's own [Rust guide](https://docs.docker.com/guides/rust/) does exactly this.

**Two "offline"s that are unrelated:** `SQLX_OFFLINE=true` makes `query!` compile from the committed `.sqlx/` cache with **no database** (real, must stay); cargo `--offline` forbids the crate registry (impossible in a bare builder). Conflating them is how the aspiration got written into a Dockerfile in the first place. The same flag is legitimate in the *openapi snapshot* step, because that job restores `~/.cargo/registry` via `Swatinem/rust-cache` — the flag is only wrong where no cache exists.

**Cache mounts do not survive a fresh CI builder.** Dockerfile reference: cache mounts are "not included in exported build cache (`--cache-to`), and are not restored by `--cache-from` … on CI runners that provision a fresh machine for each job, cache mounts start empty". Adding `RUN --mount=type=cache,target=/usr/local/cargo/registry` to this workflow would be a no-op (the real workaround is `reproducible-containers/buildkit-cache-dance`). Also: if anyone ever cache-mounts `target/`, the binary must be `cp`'d out inside the same `RUN` — a cache mount's contents are not in the layer, so `COPY --from=builder /app/target/...` would fail.

## T006 lesson (2026-11-10) — `prepare --check` is server-flavour-bound

**`cargo sqlx prepare --check` can never pass on a second-database CI leg.** sqlx-cli FORCES `SQLX_OFFLINE=false` on its inner build (so the step's `SQLX_OFFLINE=true` env is ignored there) and byte-compares the regenerated describe JSON against the committed `.sqlx/` cache — which is generated on MySQL 8.4. MariaDB 10.6 legitimately describes the same SQL differently (nullable flags for `CASE` / `COALESCE(MAX())` expressions; `EXISTS()` as INT vs LONGLONG), producing 20 compile errors at 6 sites (10 in `lib`, 10 in `lib test`); the comparison is environment-bound, not repo-bound. The `backend-mariadb` step is now an **online describe gate** — `SQLX_OFFLINE=false cargo check --locked --workspace --all-targets` after `cargo clean -p backend-rs`, because `SQLX_OFFLINE` is NOT part of cargo's fingerprint: without the forced rebuild the macros don't re-expand and the gate passes vacuously (sqlx-cli does the same via `setup_minimal_project_recompile`). Row types are made server-independent with **`!` nullability overrides in the column alias** (`AS "max_pos!: i64"`, `AS "exists!: i64"`) — a `: type` override alone does NOT pin nullability: sqlx still wraps in `Option` whenever the *server* says nullable. The canonical cache gate stays in the `backend` (MySQL) job.

## CI lesson (2026-11-14) — never apt-get install what the runner image ships

**`apt-get update` + `apt-get install mysql-client` (intended: just the CLI for a `SELECT COUNT(*)` cross-check) cascaded into a `mysql-server` 8.4.11 → 8.4.13 upgrade, whose postinst maintainer script exited 1 → dpkg error → apt exit 100 → `set -e` killed the step before the pending=0 assert ever ran (CI runs 43427944752, 43455667471).** The ubuntu-26.04 image ships both packages; the strict same-version `libmysqlclient24` dep chain pulls the server in with the client, `-qq` suppresses the inner reason, and the CI's own docker MySQL owns port 3306 anyway. **Rule: on GH-hosted runners, if you need a CLI the image already ships, `command -v <tool>` and use it — never `apt-get install` it.** If a tool is genuinely missing, pin the exact package and read the FULL apt output (drop `-qq`) so the postinst error is visible. The redundant apt block was also inconsistent with the very next step ("SHOW CREATE TABLE"), which already used the preinstalled `mysql` without installing anything.

- **A runner image update (8.4.13 publish) can break a pipeline with zero repo changes.** Both `dev` runs on 2026-11-13 failed at the same step; the last green `dev` run was 2026-11-11. When CI breaks with no matching commit, diff the *environment* (image/package publish dates) before the tree.
- **Node CI steps are now pinned to the LTS major (26 "Lithium", Active LTS since 2026-10-28), not a floating `lts/*`** — so LTS promotions are a deliberate edit of three `node-version:` lines (two in backend-rs.yml, one in frontend-storybook.yml). Note: since Node 25 the official Linux binaries link `libatomic` (preinstalled on ubuntu-26.04; may need `apt-get install libatomic1` on slimmer/older images).
