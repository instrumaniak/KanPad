- Frontend board create/edit shares one `BoardFormModal(mode)` + top-level `BoardFormFields` in `features/boards/board-form-modal.tsx`. Don't reintroduce `InlineEditForm` in `board-card.tsx` or per-mode form copies. Reset edit state via `key={edit-${id}}` remount, not `useEffect` prop-to-state sync. `BoardCard.onEdit` passes full `Board` (incl. `project_id`), modal self-fetches projects via `useProjects`.
- `npx shadcn@latest add <component>` can misresolve the `@` alias (check `info --json` `resolvedPaths`): after adding, verify placement with `git status`. Move stray `@/components/ui/*.tsx` into `src/components/ui/`, fix the generated `from "cn"` import to `@/lib/utils`, and remove the bogus `cn` npm dep it adds (`radix-ui` meta package already covers Select/Dialog primitives).
- Radix `SelectItem` values must be non-empty strings — never `value=""`. For a "No project" null-option use a sentinel (e.g. `NO_PROJECT_VALUE = 'none'`) mapped back to `null` in `onValueChange`.
- Radix `Select` in vitest/jsdom needs `Element.prototype.hasPointerCapture` / `setPointerCapture` / `releasePointerCapture` / `scrollIntoView` mocks in `src/test-setup.ts`; drive it with `user-event` click on the `combobox` trigger + `findByRole('option')`, not `fireEvent.change`. `<label htmlFor>` associates with `SelectTrigger`'s `<button>` (button is labelable), so `getByLabelText` / `getByRole('combobox', { name })` keep working after migrating from native `<select>`.
- Chained create-then-use mutations (e.g. create project → create board in `BoardFormModal`): cache the first result in a `useRef` keyed by input so a second-step failure + retry reuses it instead of duplicating/orphaning. Guard the submit handler with a synchronous `submittingRef` (React Query `isPending` flips only after re-render, so rapid double submits slip through). While any mutation is pending, block Dialog dismissal: guard `Dialog onOpenChange` in the modal shell (pending state lifted via `onPendingChange`) and `preventDefault()` `onInteractOutside`/`onEscapeKeyDown` on `DialogContent`.
- Assert navigation in modal tests by partially mocking `react-router-dom` (`vi.hoisted` for the `mockNavigate` + `importOriginal` spread keeps `MemoryRouter` real). Deterministic double-submit race test: two synchronous `fireEvent.click`s back-to-back (no `await` between) — the second handler must hit the ref guard before microtasks flush.
- Split modal close paths: user dismissal (`Dialog onOpenChange`, Cancel) goes through the pending guard; programmatic submit closes (success, pristine) use a raw `onClose` prop — the guard would see the just-set `submittingRef` and refuse to close. Cache chained-creation results in a `Map<key, id>` (not a single entry) so A→B→A rename sequences don't duplicate.

- T41 frontend migration: when a feature's hook (`use-cards`) newly depends on a helper exported from its API module (`sanitizeCardListParams`), the module-level `vi.mock('./<feature>.api')` in the hook tests must also mock that helper (or use `importOriginal`), otherwise Vite fails at runtime with "No ... export is defined on the mock".
- Frontend node_modules repair: if Vitest bus-errors after an interrupted copy/reinstall, remove `node_modules` (and stray `node_modules.bak`) entirely and `npm install` from a clean state; do not `git add -A` until verifying no ignored dependency trees are staged.
- Cutover: default backend target now lives in two places (`VITE_API_URL` in `compose.yaml`, Vite proxy fallback in `frontend/vite.config.ts`); keep both flipped together and retain the `VITE_API_URL=http://localhost:3000` override for one-line app rollback.

## Session cache hygiene (2026-11-17)
- Tag: `frontend`
- React Query keys are not user-scoped, so a session boundary (logout/login/register) must flush the whole query cache — one owner: `resetSessionCaches()` in `src/lib/query-client-reset.ts` (`cancelQueries()` → `clear()`), called **before** any new-session `['auth','me']` write. Clearing after the write just wipes it; skipping `invalidateQueries` after a clear doesn't work either — it's a no-op on an emptied cache.
- `queryClient.clear()` alone is enough to stop late in-flight responses (each query is destroyed → its retryer rejects with `CancelledError` → `setData` is never reached), but `cancelQueries()` first is kept as belt-and-braces. `clear()` does NOT cancel in-flight **mutations** — their `onSuccess`/`onSettled` still run. Two arms: (a) `invalidateQueries` against an empty cache with no observers is harmless; (b) **unconditional `setQueryData` recreates the query post-boundary — the one residual R2 path**, with live instances in this codebase (`use-cards.ts:100,107,118,152,193,204`, `drag-drop-context.tsx:83`, `use-projects.ts:54`). Accepted for T013 (out of scope), carried as an explicit requirement into T014 — see its \"Carried from T013 review\" section (sessionEpoch guard or accept-and-document).
- After `clear()`, a mounted observer still references the destroyed query; the re-attach (fresh query → `setOptions` → `build`) happens on a later effect hop. So the auth context shows the new `me` one render hop after login/register — tests must `waitFor(() => expect(result.current.user)...)`, not assert synchronously, or they flake between one and two flushes.

## Full dependency upgrade to latest (2026-11-13)

## Vite 8 `configLoader: 'native'` warning (2026-11-13)
- Tag: `frontend`
- Vite 8 warns "unsupported by `configLoader: 'native'`" for `__dirname` in `vite.config.ts` (and `vitest.config.ts`, which reuses Vite's config loader — same warning on `npm run test`). `configLoader: 'native'` (plain native Node ESM import of the config) becomes the default in a future major, where `__dirname` is undefined in ESM scope. Use `import.meta.dirname` instead (Node ≥20.11, already implied by Vite 8's engines `^20.19 || >=22.12`).
- `import.meta.dirname` works under **both** loaders: Vite's `bundle` loader rewrites it to an injected `const __vite_injected_original_dirname = <config dir>`, and native Node provides it natively. Verify with `npx vite --configLoader native` (it crashes on `__dirname` before the fix, so this is a real forward-compat test, not just a silenced warning).
- `VITE_CONFIG_NATIVE_IGNORE_WARNING=true` only hides the message (it also disables the AST checker). Explicitly setting `configLoader: 'bundle'` does **not** suppress it — the warning is emitted *by* the bundle loader itself.
- `tsc -b` covers `vite.config.ts` only (`tsconfig.node.json` `include`); `import.meta.dirname` type-checks via `@types/node`'s `web-globals/importmeta.d.ts`, but `vitest.config.ts` / `playwright.config.ts` are never type-checked.

## Global 401 handling + retry policy + timeouts (2026-11-17, T014)
- Tag: `frontend`
- Dead error taxonomy is worse than none — wire it or delete it. `error-messages.ts` was only ever called by its own test; T014 made it the single owner for user-facing error text (`getErrorMessage`), with a **server-message-wins** rule (taxonomy owns `title`/`retry`/`redirect`; `message` prefers the server's own text whenever present — required so call sites don't regress to generic copy). Browser jargon (`Failed to fetch`, `Load failed`) is filtered out by the mapper, not by call sites.
- Industry standard for global 401 handling (axios-auth-refresh lineage, TanStack Query's `QueryCache`/`MutationCache` `onError`): ONE handler, assigned ONCE to the caches (`useEffect` in a small `<SessionExpiryHandler />` mounted under the providers — TkDodo's endorsed seam when the handler needs React context); idempotent under concurrent 401s (single-flight flag held until the cache reset settles). `MutationCache.config.onError` is `(error, variables, onMutateResult, mutation, context)` — the `mutation` is the FOURTH argument, not the second (ask the types, not the docs snippet).
- **Bad credentials ARE a 401** — a global session-expired handler must exempt credential POSTs (login/register) and guest routes, or every typo'd password fires cache reset + redirect + a misleading toast (industry: suppress the global 401 UX there; the form shows its own error). We use `meta: { skipSessionExpiry: true }` on those mutations and a guest-route check in the handler.
- A `['auth','me']`-style bootstrap query is exempt only from **redirect/toast** (AppLayout owns the redirect) — never from the cache clear. An exemption that leaks the previous identity defeats the entire point of T013's clear-before-write rule. Rule of thumb: exempt the UX, never the hygiene.
- "Login fails after the server set the cookie" (non-2xx with cookie / parse failure / abort) is mostly NOT a 401 — the global-401 handler cannot cover it by design. Cover it with a silent `resetSessionCaches()` in login/register `onError` (no-op on empty cache). Belt-and-braces is cheap; reasoning about "can't happen" is expensive.
- Post-boundary mutation rollbacks recreate queries via concrete-value `setQueryData` (the `MutationCache.clear()` caveat from T013) — but the live instances were only the `onError` rollbacks. Verified against `@tanstack/query-core@5.107.1` source: an updater returning `undefined` is a no-op, a defined result calls `cache.build()` (recreates the query). Fix: a `sessionEpoch` counter bumped by `resetSessionCaches()`; `onMutate` captures it in context; `onError` skips the rollback when the epoch changed. "Rollback guards need the epoch, not a global rewrite of every feature file."
- A global "session expired" handler that fires on a shared workstation must leave ZERO residue of the previous user: cache (T013) + in-flight rollback writes (this task) + redirect to `/login`. One teardown, two callers (logout button and the 401 path).
- Default timeouts: 15 s default in `apiFetch` via AbortController; caller-signal chaining re-throws the *caller's* abort unchanged — only the internal timer abort is re-labelled as a typed `TimeoutError` (retry predicate: network-class, once; 4xx and `CancelledError`: never). Retry policy lives in `app-query-client.ts` (single owner for the App's QueryClient defaults) so tests can pin it: 500 → retry once, 400/401 → no retry, mutation → never, `CancelledError` → never.
- Review H1 lesson (2026-11-17): **a single-flight flag must never arbitrate eligibility decisions.** Holding `inFlight` across an `await` while returning "already handled" for overlapping errors means whichever 401 arrives first (often the exempt me/guest one) silently starves a racing actionable 401 of its navigate/toast. Fix that held up under red-proof: exempt (idempotent) paths run concurrently WITHOUT the slot; only the side-effect-bearing path single-flights. Test the race deterministically by driving `QueryCache.config.onError` directly in one synchronous burst — wall-clock concurrency tests are scheduling-dependent and will lie to you in both directions.
- `MutationCache.config.onError` is `(error, variables, onMutateResult, mutation, context)` — `mutation` is the **fourth** argument (the first smoke version read `.meta` off the variables slot and threw on every mutation 401).
- Login/register `onError → resetSessionCaches()` deliberately fires on EVERY failed login (incl. typos): flush + epoch bump, no-op on empty cache. Fail-safe, not a bug — don't "fix" it into conditional wiring without replacing the carried-item-#2 guarantee.

## Board error states + navigation-reset route boundary (2026-11-17, T015)
- Tag: `frontend`
- **Query errors never reach an error boundary by default** (TanStack v5 `throwOnError` is the opt-in). Every query-owning view needs its own `isError → ErrorState+refetch` branch, or a failed fetch renders as the *identical-looking* empty state — the most common React Query bug in production ("silent empty board" indistinguishable from a real empty board). Boundary = render crashes; `isError` = fetch failures. Complementary, both required.
- **Decompose 4xx, don't collapse:** 404 → not-found view, no retry (permanent); 401 → a global session-expiry handler owns the redirect UX (feature code renders nothing but the loading state — never its own 401 error UI, that's double-handling); everything else (5xx/network/`TimeoutError`) → `ErrorState` + retry. The retry button on a permanent 404 is a lie the user clicks forever.
- **`useLocation()` is impossible in `App()`** when `App()` renders `<BrowserRouter>` — the location-dependent boundary wiring needs a small wrapper component that renders *inside* the router (industry pattern: `<RouteErrorBoundaryWithLocation>` with `resetKeys={[location.pathname]}`; chosen over `key={pathname}` remount — resetKeys is a targeted flag clear, key is a demolition).
- **Hand-ported error boundary ≠ upstream `react-error-boundary`** unless you port the whole semantics: the `prevState.didCatch` guard (never reset on the commit that caught the error) is the piece people drop. Without it, a crash in the same commit as a `resetKeys` change resets immediately → children re-render → the deterministic crash fires a second time in that same update. Port the guard; test it with a same-commit crash+key-change case.
- **When counting effects of a boundary reset, `componentDidCatch` calls are the metric — not child invocations.** React re-invokes the crashing child several times during its internal error recovery passes, so a `throwCount` of 3 does not mean a double crash; `componentDidCatch` fires exactly once per caught crash. Assert on `console.error` calls with the exact `'RouteErrorBoundary caught:'` prefix.
- **React Router v7 wraps navigation state updates in `startTransition`** — a bare `act(() => navigate('/x'))` may never flush the pathname change to the tree (observed: wrapper re-render count of zero). Drive test navigations through a real React event (`fireEvent.click` on an always-mounted nav button / link) — that's also the highest-fidelity path (real user click).
- **`ErrorState` inline beats empty-state swap for partial-page failure:** in a list page, render the error inside the scroll area so the page chrome (title, create button) stays interactive — the user can still create/navigate away while the list is broken.
- **Error branches must gate on data absence, not just `isError`.** React Query v5 keeps `data` when a background/refetch fails (`isError:true` with last-good `data` present). An unguarded `isError → <ErrorState/>` swap hides a perfectly good board behind an error card on every invalidation hiccup (e.g., a mutation invalidates `['columns', id]` and the refetch 5xx's post-retry). Render the error card only when there is nothing to show: `(boardQueryError && !boardResponse) || (columnsQueryError && !columns)`, `isError && !data` for lists — while keeping the full-screen error for initial-load failure. Caught in independent review (M1); pinned by cached-data regression tests.
## Bundle: route chunks + pele swap + CI budget gate (2026-11-17, T016)
- Tag: `frontend,bundle`
- **A `codeSplitting.groups` catch-all with no `test` (`name: 'app'`) matches EVERY module, entry included** — it merges all route-level chunks into one entry and defeats `React.lazy` entirely. Both were in `vite.config.ts`; removing the `app` group restored route-level chunks. Initial gzip went ≈1.84 MB → 167 KB (lazy routes) → **257,986 B** after the second amendment (all app routes static — perceived snappiness over minimal bytes; user's call). A catch-all `vendor` is not automatically a bug, though — what matters is *scope*: the second amendment deliberately re-introduced one `vendor` group that excludes the markdown/pele family (an explicit `LAZY_ONLY_PACKAGES` set, computed from the prod dependency closure with cross-family consumers carved out), giving 1 vendor request on the initial path with markdown/pele still lazy. **A group without a `test` is a black hole; an unscoped `test` is a leak — scope every group you write, and if you merge vendors, enumerate what must stay out.**
- **A `modulepreload`-only budget gate silently waives the entry** (entries are never modulepreloaded). The gate must count the entry `<script type="module" src>` plus every `modulepreload` href — that is the true initial set. `scripts/check-bundle-budget.mjs` does both; its unit tests pin the entry-only-over-budget case.
- **Red-proof the gate at the real boundary, not a proxy one.** Temporarily importing pele inside `mermaid-diagram.tsx` (a lazy chunk) does NOT trip the initial-load gate — pele landed in the lazy markdown-renderer chunk. The honest red-proof is a temporary eager import in the entry (`App.tsx`): entry ballooned to ~300 KB gzip over the entry budget → gate exits 1 with per-chunk + total failures → revert. Red-proof what the gate is for.
- **An exclusion set does nothing if something eagerly imports the excluded family.** T016's `LAZY_ONLY_PACKAGES` was "correct" on paper — but the board card face (`CardPreview`) statically imported a react-markdown-based title renderer, dragging micromark into the *entry* (~30–45 KB gzip on every page, every visitor, even /login). An exclusion is a promise about the *graph*, not the config — verify it by grepping the built artifact for markers (`urlTransform`, `micromark`, `hastscript`) and by reading the chunk the entry actually ships. If the excluded bundle is needed eagerly, the answer is a smaller eager renderer, not a bigger exclusion.
- **Budget numbers are measure-then-set, not aspirational.** The old "300 KB initial" target was only meaningful pre-measurement. Measure post-fix, set gate = measured + ~15–20 %, per-chunk = largest initial-load chunk + headroom. T016 went through three ratchets in one day (221,534 → 167,385 after the vendor-react regex fix → **257,986 B** after the all-static second amendment, final gate **310,000 B / 225,000 B**). The gate is a regression guard, not a vanity target — put the justification in Notes and say so in the spec amendment.
- **"Everything snappy" trades first-load bytes for zero round trips — do it deliberately.** Making all nine routes static moved the initial gzip from 167 KB (lazy routes) to **258 KB** (final, after the B1 fix — still <2×, and ~50 KB more would be the price of eager markdown) but removed every route-level Suspense flash and one request per route flip; the markdown renderer + pele stayed lazy (notes/card-panel only). Measure, keep them isolated via an explicit `LAZY_ONLY_PACKAGES` set in the bundler config, and gate the initial path — then the heavy path is free until used.
- **An over-capturing chunk-group regex silently flattens lazy boundaries and can pass every gate.** `/node_modules[\\/]react(?:-dom|-compiler)?/` has no trailing boundary — it captured `react-markdown`, `react-router`, `react-day-picker` into the *initial* vendor-react chunk (caught in review; entry-level split looked fine). Boundary-anchor the group (`(react|react-dom|scheduler)[\\/]`) and re-measure before believing the numbers.
- **Replacing a heavy renderer beats lazy-loading it.** mermaid (~1.36 MB gzip) fully disappeared via pele (`pele/lazy`, per-type chunks on demand, zero runtime deps, MIT, Obsidian team). `MermaidDiagram` kept its name/fence/API; only the internals changed (`renderAsync`, sanitized `useId()` idPrefix, exact font strings shared with `--pele-font`, `images: false` against hotlink tracking pixels, DOMPurify retained as defense in depth, `PeleError` → static fallback that never echoes source).
- **Storybook browser-mode tests can fail 7/54 with 15 s timeouts under contention and pass 54/54 on a quiet re-run** — don't ship the failing run; re-run and only then judge. If it recurs, raise `testTimeout` deliberately.
- **Rolldown-built production timings beat dev-mode vibes.** `/login` felt "slow" in dev (13 s to form — vite dev transforms on the fly); the production build via `vite preview` interacted in ~1.4 s with 221 KB gzip initial JS (167 KB after the regex ratchet). Measure the artifact, not the dev server.
- **DOMPurify's default config passes `<style>`** (and `<image>`). pele 1.13.0 never emits them in our configuration (no `url(` in style attributes, `images:false`), but the default is one fast-moving-1.x release away from a real gap — pass `FORBID_TAGS:['style']` in the sanitize call and pin it with a test on the rendered output.
- **Protocol-relative URLs (`//evil.example/x`) pass both pele's scheme allowlist and DOMPurify's `ALLOWED_URI_REGEXP`** — click-required, `rel="noopener"` mitigates, accepted and documented rather than wrapped. Also: DOMPurify default strips pele's `target="_blank"` (links open in-tab; `rel="noopener"` kept — fine), and `pele`'s `mount()` does **no** sanitization by default and renders the error message directly — never use `mount()` without a `sanitize` fn; `render()` + DOMPurify (what the app uses) is the safe path.

## Anonymous me fire storm on guest routes (2026-11-18, T043)
- Tag: `frontend,auth`
- A guest page must never pay more than **one** `GET /api/auth/me` per load (two in dev StrictMode). Ours fired ~44 in ~3 s (~840 in ~1.5 s in a jsdom repro) because the global 401 handler's exempt (clear-only) branch called `queryClient.clear()` for **every** 401 — including the one the bootstrap `me` query itself produced. `clear()` destroys the query; the mounted provider re-subscribes via `setOptions → #updateQuery → cache.build()` on the next render, `query !== prevQuery` + stale data-less query ⇒ immediate refetch; 401 ⇒ clear ⇒ … self-sustaining, no StrictMode needed. Exhausted T007's per-IP rate limiter ⇒ anonymous visitors locked out of login.
- **"Exempt the UX, never the hygiene" needed one carve-out:** an exempt 401 whose trigger is a **data-less** bootstrap `['auth','me']` query must not destroy that query — destruction IS the loop. Sparing by `queryHash` only when `query.state.data === undefined` keeps the guarantee in both directions: a focus-refetch of `me` that 401s with last-good data in cache (TanStack keeps `data` on refetch error) is still destroyed like everything else — zero stale identity on a shared tab, at the cost of exactly one extra bounded refetch.
- Sparing must be conditional on **no data + bootstrap-me key** — not on "the trigger was exempt" generally: sparing an arbitrary exempt trigger on a guest route would let a mounted, errored user-scoped query (boards/notes) survive the flush on a shared tab.
- The exemption lives in `resetSessionCaches(queryClient, { exceptQueryHash })`: epoch bump → `cancelQueries()` → remove all queries except the spared one (and only if it is data-less) → `mutationCache.clear()`. With no `exceptQueryHash` (or the spared query holds data) it falls back to the exact old `clear()` path — T013/T014 guarantees (logout/login/register full flush, mutation-rollback epoch guard) unchanged; actionable 401s untouched; exempt paths still take no single-flight slot.
- Testing the loop deterministically: mount `AuthProvider` **with** `SessionExpiryHandler` + failing `meApi` (a 401) and assert the fetch count after quiescence (`meApi` called exactly once). Directly driving `QueryCache.config.onError` with a fake query (`{ meta: { skipSessionExpiryRedirect: true } }`) misses the refetch cycle — the repro only appears with the real mounted provider. Live check: Playwright request counter on `/login` → 1 `me` call; 30 s idle stays 1; guest navigations add exactly one each; register auto-login adds zero; reload of `/` adds exactly one; no 429s.
- Reading the installed source beats the docs: `QueryCache.clear()` ⇢ `query.destroy()` ⇢ silent cancel; the re-fetch happens in the observer's `setOptions` effect (`#updateQuery` → `cache.build()` → `shouldFetchOptionally` when `query !== prevQuery` and `isStale`), not in the subscription path — `useSyncExternalStore` never re-subscribes by itself.

## Virtualization + dnd-kit + dragOver throttling (2026-11-19, T021)
- Tag: `frontend,perf`
- **`SortableContext items` is the FULL ordered id list, never the virtual slice** — `useSortable` computes `index = items.indexOf(id)` and `getSortedRects` iterates it; a visible-only slice shifts every index and desyncs transforms, keyboard coordinates and the announcements' full-list positions. `verticalListSortingStrategy` is the only sortable strategy that supports virtualized lists. `DragOverlay` (already portalled here) absorbs the lifted preview — unaffected by virtualization.
- **The virtualizer's `translateY` and `useSortable`'s `transform` must not fight:** outer absolute virtualizer cell (`position:absolute; top:0; transform: translateY(row.start)`) + inner sortable node (its own transform) — or split `translate:`/`transform:` on one node. `SortableContext` ids stay stable (`card-${id}`), `getItemKey = card.id` keeps the measurement cache attached to cards across reorders.
- **react-virtual has no `stickyIndices`:** pin the dragged row (and, in the list view, the inline-edit row) with a custom `rangeExtractor` that unions `defaultRangeExtractor(range)` with the active index, or dnd-kit loses its measured node mid-drag and the editing input unmounts mid-focus. Keep the source row mounted but dimmed (`opacity: 0.5` from CardDraggable) until the drop.
- **`useVirtualizer` before any early return** (hook rules) — the empty-column `return null` lives below the hook. `estimateSize` should be an upper bound of the measured row height (dynamic rows via `measureElement` + `data-index`); underestimating causes scroll jumpiness. `overscan ≈ 5`. The TanStack Virtual + React Compiler interplay logs one `react-hooks/incompatible-library` warning — benign, the compiler just skips memoizing that call.
- **jsdom cannot virtualize on its own** (`outerSize === 0` → `calculateRange` returns null → zero rows; rows also measure to `offsetHeight: 0` and expand the window to everything). Tests must mock `clientHeight/clientWidth` (feeds `observeElementRect`'s `getRect`) **and** `offsetHeight/offsetWidth` (feeds `measureElement`). Assert on `aria-rowcount`/`aria-rowindex` for full-list semantics; real-browser bound proven by the `virtual-card-row` count (13 of 500 mounted).
- **`setQueryData` applies `replaceEqualDeep` structural sharing by itself — but a no-op write still dispatches and re-renders subscribers.** Skip the call entirely when no order changed: find the current source column first (it may be the drop target after optimistic live moves), and if source === target (or target missing), return the SAME array reference and don't call `setQueryData`. Reindex positions only for cards whose position actually changed (`c.position === i ? c : {...c, position: i}`) — unchanged cards keep object identity and memoized children skip re-rendering. Re-spread only the two columns whose arrays changed; unrelated columns keep their references.
- **rAF coalescing for pointer-rate events:** overwrite a single `pendingEvent` ref and schedule at most one `rafId` per frame; cancel the pending frame on `dragStart`, `dragEnd`, `dragCancel` and unmount (dragEnd does its own authoritative writes — a stale pending dragOver must never land after them). Tests stub `globalThis.requestAnimationFrame`/`cancelAnimationFrame` and drive synthetic events directly through the captured DndContext props (a `vi.hoisted` handler-capture mock of `DndContext`); assert writes == 0 mid-burst and ≤ 1 after a flush. jsdom needed no rAF polyfill for this.
- **A virtualized list with an unbounded scroll element mounts everything — virtualizing is inert.** The bounded-height chain must exist first (this task pulled T044's Stage A in with sign-off: BoardView-scoped `h-full min-h-0` + `flex min-h-0 flex-1 flex-col` on the transition wrapper + `h-full min-h-0` scrollers, and `column-droppable.tsx` root `flex min-h-0 flex-1 flex-col`; T044 keeps Stages B1–B4).
- **`sortable.index` is stale during keyboard drags** (useSortable derives it from the cache order, which same-column drags never write — it stays at the drag-start index for the whole gesture). Any custom coordinate getter keyed off `active.data.current.sortable.index` is built on stale data — do not "fix" keyboard behavior that way. **`sortableKeyboardCoordinates` is the right getter and moves the card exactly one row per ArrowDown**; dnd-kit only considers mounted rects, so boundary behavior depends on overscan/window mounting (rows past the mounted range get no valid target — the press is a no-op). Verified e2e on a 120-card column: 24 ArrowDowns → exact index 24 across the virtual boundary, focus preserved, persisted (API + reload). An earlier custom getter "fixed" a dead-end that didn't exist and introduced a far-worse failure (scrolling the window 20+ rows past the drag; the drop then computed `insertIndex` from a distant `over` and landed the card 12 rows beyond where it was dragged). Rule: prefer the library's getter; if the boundary case ever truly breaks, fix it at the dnd-kit level (or migrate to `@dnd-kit/react`), never by intersecting stale indexes with mounted rects.
- **e2e ordering pitfall:** after a dnd-kit keyboard drop, `handleDragEnd` fires the mutation from React state — an immediately following non-browser API GET can observe PRE-drop state. Wait for the PATCH (`page.waitForResponse(r => r.request().method() === 'PATCH' && /\/cards\/\d+/.test(r.url()))`) before asserting persisted order; the UI's optimistic reorder races it.
- **500-card smoke on a throwaway tmpfs MariaDB (`--tmpfs /var/lib/mysql`, own container + root password, `kanpad_e2e` schema, own port; never the dev DB):** 13 mounted rows board/list, TTI ≈ 1.2 s. Numbers are T026's baseline (recorded in T026's task file). Bundle gate re-checked after adding `@tanstack/react-virtual`: initial gzip 267,673 B (+9.7 KB) vs 310,000 B cap — green.
- **React Query's `replaceEqualDeep` returns the prev reference on structural-share hits — but a no-op `setQueryData` still dispatches** (new state object, `dataUpdateCount++`, per-observer `updateResult`, cache-level notify). Skipping the call (same-reference check) is the correct primary guard; treat React Query's short-circuit as a secondary backstop only.
- **`useVirtualizer` in the virtual list and dnd-kit over a virtual window:** an ArrowDown requires a *mounted* rect to land on — the keyboard sensor cannot move to an unmounted row, and `sortableKeyboardCoordinates` has no behavior when nothing is below the dragged node (not even auto-scroll). Fix with a wrapper coordinate getter: when the ±1 neighbor is unmounted, scroll the innermost scrollable ancestor one row instead of moving; else delegate to the stock getter. Also: `useVirtualizer`'s source scroll element must itself be bounded (T044 Stage A) — otherwise virtualization mounts everything and the whole exercise is inert.
- **React Compiler (compiler-driven memoization) + `@tanstack/react-virtual`:** the `react-hooks/incompatible-library` warning is benign — the compiler skips memoizing the component using `useVirtualizer`, no stale closures are produced. Interim guidance stands: don't hand-memo everything; memoize the *inputs*.
- **Every `rangeExtractor` pin union must be deduped** (`new Set([a, b])`): the dragged row is *also* the focused row during every keyboard drag, and the editing row is also the focused row after `startTitleEdit` pins it — `[draggedIndex, focusedIndex]` = `[i, i]` would put the row in the rendered range twice, producing duplicate React keys (`key={virtualRow.key}` collides) and duplicated rows (`[...base, ...missing].sort()` is ascending but not unique). A duplicate key silently corrupts reconciliation — it shipped as a duplicate-render + console error in the keyboard e2e. Regression-tested in both views.
- **Inline `getItemKey` breaks the virtualizer's measurement memo** — `getMeasurementOptions` keys on `getItemKey` by reference, so an inline arrow function forces an O(n) rebuild of the flat typed array per render (every drag frame). `useCallback` it and never return a bare `index` fallback (use a string-typed `__i_${index}`).
- **Element relocation resets `document.activeElement` in jsdom** (`insertBefore`/`appendChild`): virtualized lists that relocate pinned rows between renders will fire blur→commit in jsdom but NOT in real browsers. Don't assert live focus in jsdom across virtual-window shifts; assert row presence instead — the focused-row pin is what actually protects keyboard users in a real browser.
- **Focus pinning for virtualized lists needs three separate rangeExtractor unions, one per interaction:** dragged row (board lists), editing row and focused row (list view). A focused, non-pinned row unmounted under Tab navigation drops focus to `<body>`; pin via `onFocusCapture`/`onBlurCapture` + a union in `rangeExtractor`, and restore focus to the title button after inline-edit commit/cancel via a ref map + pending-restore ref.

## Column footer placement: flex-grow pins the footer — size the scroll box to content (2026-11-20)
- Tag: `frontend,css,layout`
- Symptom: "+ Add a card" sat pinned to the column's full height even for near-empty columns (198–642 px of dead space above the button). Root cause was the height chain, not the footer: `column-droppable.tsx` root `flex-1` **plus** the column scroller's `flex-1` stretch the scroll box to the fixed `h-full` column, so the last flex child (the footer) always lands at the bottom.
- The fix needs **both halves**: (1) drop `flex-1` from the scroller → `flex: 0 1 auto` (content-sized; `min-h-0` still lets it shrink when content overflows, which is exactly when the footer must pin to the visible bottom); (2) move the footer **inside** the droppable so the dnd drop zone keeps header→column-bottom coverage. Shrinking the droppable instead (candidate B) looks pixel-identical but collapses the drop target to content height — measured 16 px on an empty column — silently breaking drag-to-empty-column.
- Flexbox mechanics behind it: positive free space goes only to `flex-grow` items (so slack parks *below* the footer inside the droppable — still a drop target); negative free space is absorbed by the `min-h-0` scroller while header/footer keep their automatic min-content size. No `margin-top:auto`, no absolute positioning, no JS measurement.
- Verify layout claims with **geometry, not screenshots**: jsdom sees none of it. The red-proof e2e (`e2e/column-add-card-placement.spec.ts`) measured the pre-fix gap at 198 px vs the required ≤ 60; post-fix assertions: short column `btnTop − lastRowBottom ≤ 60` and `colBottom − btnBottom > 100`, overflowing column `≤ 20` + internal `scrollHeight > clientHeight` + bounded virtual rows, droppable bottom within 2 px of column bottom in every column, and the T044 containment guard (`main.scrollHeight === main.clientHeight`).
- **Plan-mode-safe probe pattern (reusable):** validate candidate fixes by *runtime-only* DOM patching in `page.evaluate` (`classList.remove('flex-1')`, `appendChild` move) against the live app — measurements + screenshots for both candidates before touching source; React never re-renders during the probe so the patch holds.
