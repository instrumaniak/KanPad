## DB data & migration safety first

- development, testing, production - all must follow the exact db migration patterns for safe, reproducible data persistence behavior.

## Backend E2E Test Pattern: Must Always Verify DB Persists

- For ALL data modification endpoints, tests MUST verify actual database state, not just API response.
- For every PATCH/POST/DELETE test, add ONE additional assertion that verifies persistence via a different API call or DB query.

## Frontend API Layer Conventions

- API response types (`ApiResponse<T>`, `ListResponse<T>`, `ApiError`) must be defined in `@/lib/api`, not duplicated across feature API files.
- Use `apiFetch<T>()` helper instead of raw `fetch()` + `handleResponse()` in API files.
- Don't copy-paste `FETCH_OPTIONS` or `handleResponse` into each API file.

## React Query Conventions

- Use targeted cache invalidation (`['columns', boardId]`) not global (`['columns']`) unless you need to invalidate all instances.
- When multiple handlers read from the same cache, capture original state at interaction start in React state. Don't assume cache is unchanged between handlers.
- In drag-drop code, `handleDragEnd` must use `dragSource` state from `handleDragStart`, not `getColumns()` which may be stale.

## Frontend E2E Test Patterns

- Test setup (creating boards, columns, cards) must use API calls, not UI interactions. UI is only for the behavior under test.
- Never use `waitForTimeout()` in E2E tests. Use `waitForLoadState('networkidle')`, element assertions, or `page.waitForSelector()` instead.

## Frontend Code Quality

- Use Radix UI components (`DropdownMenu`, `Dialog`) for menus and modals instead of manual implementations with `useRef` and absolute positioning.
- Don't use `document.querySelector` for focus management - use React refs or callback props instead.

## Rust Backend Test Harness

- **Single owner per transport.** In-process suites (`axum::Router` + `tower::ServiceExt::oneshot`) get all plumbing from `backend-rs/tests/api/helpers.rs`. Black-box suites (raw TCP) get the transport-independent pieces from `backend-rs/tests/api/wire.rs`. Never re-declare a helper locally — the ownership header in `helpers.rs` lists the exact forbidden set AND the sanctioned exceptions.
- **A suite MUST NOT reuse a name from the forbidden set.** The forbidden set is scoped to the IN-PROCESS suites; a local helper is only allowed when it is genuinely suite-specific, and then it must (a) take a name outside the forbidden set and (b) be listed in the header's "Sanctioned exceptions". A suite that shadows a shared name (`json_body`, `send`, `register`, `json_of`, `cookie_jar`, …) is a silent drift even when it compiles — that is how `auth_register.rs`, `throttle.rs` and `e2e_rest.rs` ended up with near-duplicate plumbing.
- **Import EXPLICITLY, never glob.** `use super::helpers::{app_on_pool, send, …}` — a glob import lets a leftover local definition silently shadow the shared one, while an explicit import makes it a hard `E0255` compile error. That compile error IS the regression guard; a glob import removes it.
- **Every `assert_problem` call takes a `what` label** naming the failing step, so a failure identifies the scenario instead of a line number. Keep the label short and specific.
- **Wire vs in-process problem assertions share one core.** `helpers::assert_problem_fields` is the single assertion core; `helpers::assert_problem` and `wire::assert_problem` are thin adapters that only differ in how they read the `Content-Type`. Add new problem assertions to the core, never to one adapter. Same pattern for the cookie jar: `helpers::cookie_jar_from` is the core, `helpers::cookie_jar` / `wire::cookie_jar` are the per-transport adapters.
- **Pick the shared variant, don't re-implement it.** `helpers::send` (owned router), `helpers::send_ref` (borrowed router — for a suite driving ONE app repeatedly, e.g. the throttle flood probes), `helpers::send_json` (pre-parsed body). The wire-flavored body parser is `WireResponse::json(what)`. If a suite needs a fourth shape, add it to `helpers.rs`/`wire.rs` — do not write a local copy.
- **Session rows are per-database, not server-global.** The store follows the pool's database (`AppState::with_pool`), so under `#[sqlx::test]` each test has its own `sessions` table. Never blanket `DELETE`/`UPDATE`/`DROP` it — scope session SQL by `WHERE id = ?`.
- **Never hardcode the session table's schema/table names in a test.** Use the unqualified `sessions` (the app database) — the store's own defaults (`tower_sessions`.`session`) are NOT what the app uses.
- **A test that binds a port binds an EPHEMERAL one.** Use `wire::bind_blackbox()` (port 0 → OS-assigned) and drive `listener.local_addr()`; never a fixed `:3001`. Cargo runs the suites in one binary in parallel, so a shared fixed port collides, and it also breaks when a dev server already holds that port.
- **Editing an applied sqlx migration is a checksum break.** sqlx stores a SHA-384 of each migration's bytes in `_sqlx_migrations` and refuses to re-run a migration whose bytes changed (`VersionMismatch`). A DB migrated with the old baseline must be DROPPED and re-migrated — never hand-edit `_sqlx_migrations`. The baseline is a squash (cutover always builds a fresh DB), so an empty target is unaffected.

## Lessons Learned

### Data migration dry-run (2026-10-20, prod_04 dump)
- `docs/data-migration-live.md` rewritten for a human operator (numbered steps + ✓-expectation lines + troubleshooting table). Keep it human-readable: every command gets an "expect" line, deep internal rationale lives in one "why" box or the appendix, not inline.
- AUTO_INCREMENT reset is unnecessary: explicit-ID INSERTs auto-raise the counter on MySQL 8.0+ (InnoDB) — the runbook's old §6 ALTERs were dropped in favor of one verification query.
- Text-fidelity gate across a latin1→utf8mb4 move must compare TEXT equality (`a.x<>b.x`), not raw HEX bytes: MySQL's latin1 is cp1252-flavored, so a bare `0x92` byte correctly expands to `E28099` (U+2019). Byte-HEX equality false-fails on those rows; only 1 row in prod_04 diverged byte-wise (and improved).
- MySQL 8.0 client accepts MariaDB's mysqldump sandbox line (`/*M!999999\- enable sandbox mode */`) without error — fallback sed-strip is documented in troubleshooting anyway.
- Prod data facts (prod_04): 2 users, 14 tables (12 app + `session`/`typeorm_migrations`); zero emoji (`F09F`), one cp1252 `0x92` curly quote, 4 note bodies already contain `?` mojibake from the latin1 era (pre-existing loss, not migration-caused — stated explicitly in the runbook).
- Human-executable checklist aside: migration readiness still owes the MariaDB 10.6 staging proof (T02b AC-b) and T51 drill timings before real cutover.

### Data migration live re-run (2026-10-21, real prod_04 dump) — 6 runbook defects found by EXECUTING it
- **A runbook is only as good as the last person who ran it end-to-end.** The first rewrite looked authoritative but had never been executed top-to-bottom; running the real dump surfaced 6 defects that reading did not.
- **A verification gate must be ordered against every mutation that precedes it.** The default-label seed (INSERT, adds rows) sat BEFORE the row-count parity gate, so `labels` read 0 instead of 1 on real prod data. The doc's own §11 had hand-waved this ("the gates ran *before* the seed"). Fix: reorder (verify → seed) AND give the mutated table its own seed-aware gates (source-labels-preserved / only-defaults-added / all-six-present / delta reconciliation). A gate that is silently order-dependent is worse than no gate.
- **AUTO_INCREMENT safety is `counter >= max(id)+1`, NOT `==`.** Explicit-ID INSERTs set the counter exactly (MySQL 8.0, MariaDB 10.6 → the manual `ALTER TABLE … AUTO_INCREMENT` step is unnecessary), but `innodb_autoinc_lock_mode=2` (default) reserves a *BLOCK* of IDs for a multi-row auto-ID INSERT → the counter can legitimately overshoot (reproduced: 6-row batch on a fresh table → max_id 6, next 8). Only a counter BELOW max+1 is a real collision risk. Never gate on equality.
- **`GET /api/v1/cards` does not exist — only `POST /api/v1/cards`.** The card LIST route is `GET /api/v1/columns/{colId}/cards`. A doc that tells the operator to curl a 405 endpoint will read as a failed migration. Always grep the actual axum router (`src/features/*/routes.rs`) before writing an API command into a runbook.
- **The session cookie name is env-dependent: `kanpad.sid` (dev/test) vs `__Host-kanpad.sid` (production only)** — `Settings::session_cookie_name()`. `__Host-` implies `Secure`, which browsers only accept over HTTPS, so the dev name is REQUIRED for a plain-HTTP staging box. A runbook must not tell the operator to look for `__Host-` while its own `.env` says `APP_ENV=development`. **The rename landed in T54:** `connect.sid` was express-session's default, copied from the Nest source (`backend/src/main.ts:39`), and a Rust service must not name its session cookie after an Express middleware. See `specs/api-rewrite-rs-specs/54-rust-idiom-hardening.md` §A2.
- **The runtime-mode env var is `APP_ENV`** — a Node.js convention (`NODE_ENV`) is not carried into a Rust service. **Landed in T54**: `APP_ENV` (values unchanged `development|test|production`), with boot **failing** when `NODE_ENV` is present in the environment (the error names `APP_ENV`), because `APP_ENV` would default to `development` and a stale deployment would otherwise silently lose `Secure` cookies + the `__Host-` prefix + prod HSTS + the deny-all CORS default. The Nest service keeps `NODE_ENV` — separate container, separate runtime. See `54-rust-idiom-hardening.md` §A1.
- **`migrate info` prints `applied: 2 pending: 0`** (2 = migration FILES, not tables). Quote the literal output in the runbook, not a paraphrase.
- **Queries with unqualified table names need an explicit "connect to <db>" instruction** in the runbook — otherwise `Table 'cards' doesn't exist` reads as a failed migration. Same class of error as a wrong HTTP route: the runbook must name the connection context.
- **Prod user 1 has a label named "Bug" with colour `red`** (the default is `blue`). The seed matches on NAME only (same semantics as Rust's `ensure_default_labels` → `INSERT IGNORE` on `UQ_labels_user_name`), so it is skipped — the two users end up with different "Bug" colours. Not a defect; document it so an operator does not "fix" it.
- Ownership scoping is not data loss: on prod_04, user 1 sees 9 of 10 boards and 2 of 3 projects, user 2 sees the rest. Always state the expected per-user split next to the row counts.
- **MySQL 8.0 caches `information_schema.TABLES` for `information_schema_stats_expiry` seconds (default 86400 = 24 h) — `AUTO_INCREMENT` read STALE can make a healthy table look broken.** Observed: right after the label seed, `labels` read `AUTO_INCREMENT = 22` while `MAX(id)` was 27 and the true counter was 29; the AUTO_INCREMENT gate failed on a database with no collision risk. Fix: `SET SESSION information_schema_stats_expiry = 0;` before the query (or `ANALYZE TABLE <t>;` first). **Any gate that reads `information_schema` must neutralize the stats cache first**, or it will report a value that never existed.
- The bcrypt → Argon2id in-place upgrade was PROVEN end-to-end (bcrypt row → 200 login → row reads `$argon2id$v=19$` → session row lands in the APP database's `sessions` table, confirming the 2026-10-19 store change).

### Data migration path comparison (2026-10-21, prod_04) — schema-first beats in-place delta
- **The dump file is ALREADY UTF-8 — `mysqldump` transcodes latin1→utf8mb4 when it READS the tables.** Byte scan of `raziurco_kanbanflow_prod_04_full-2026-10-18.sql.gz`: valid UTF-8, one `U+2019` as `E2 80 99`, **zero** raw `0x92` bytes. Consequences: (a) restoring it into a `latin1` scratch DB *re-narrows* it to cp1252 bytes — that is deliberate, it makes the scratch a **byte-exact prod replica** (the reference side of the fidelity gates); (b) restoring it into a utf8mb4 DB yields **identical text** (0 diffs on every text column of every table). The latin1→utf8mb4 conversion therefore happens in the **import step's client charset** (`SET NAMES utf8mb4` + utf8mb4 target columns), NOT in a `CONVERT` step — `0002_convert_to_utf8mb4.sql` is a **no-op on the target** (the baseline already creates utf8mb4 tables). Don't add a CONVERT pass to the target "to be safe".
- **`sqlx migrate run` on a populated DB fails with `1050 (42S01): Table 'sessions' already exists`, and the failed run leaves a DIRTY journal row.** `0001_baseline.sql` has no `IF NOT EXISTS` by design (fail fast on drift) and **sqlx 0.8.6 has no `stamp`/mark-applied command** (still an open upstream feature request), so the Rust schema can only ever be built on an EMPTY database. sqlx writes the `_sqlx_migrations` row *before* running the migration → the failed run leaves `version=1, success=0` and every later run dies with `migration 1 is partially applied; fix and remove row from '_sqlx_migrations'`. **Recovery: `DELETE FROM _sqlx_migrations WHERE success = 0;`** then drop & re-create the DB. Never hand-edit a `success=1` row (checksums are SHA-384s over the file bytes — sqlx-core `migration.rs`).
- **Three candidate paths, one result — build the schema from the migrations, don't reshape it by hand.** (A) scratch latin1 → fresh migrated DB → `INSERT … SELECT`; (B) restore → convert → 13-statement in-place `ALTER` delta → hand-stamped journal; (C) restore latin1 → `CONVERT TO utf8mb4`. All three produce **identical text on all 12 app tables** and identical row counts; B's *schema* also matches the migration-built schema on all 13 tables except column/index ORDER and the `AUTO_INCREMENT` counters. **B was not adopted**: it needs a hand-written delta script re-verified whenever `0001_baseline.sql` changes (a first draft shipped a renamed-but-still-single-column index — only a schema diff caught it) plus a hand-inserted journal that rots the moment a migration file is touched. Schema-first buys "the prod schema is exactly what the baseline says" for free.
- **A hand-stamped sqlx journal IS possible (know the escape hatch, prefer not to use it).** sqlx 0.8.6 checksum = `Sha384::digest(file_bytes)` (`sqlx-core-0.8.6/src/migrate/migration.rs:25`); stamping both rows with the computed SHA-384 makes `migrate info` report `applied: 2` and `migrate run` a clean no-op. Treat it as an escape hatch, not a procedure: the stamp silently rots on the next edit of a migration file.
- **MySQL DDL rules for reshaping indexes (all three reproduced on MySQL 8.4):** (a) `DROP INDEX` on an index that backs a FK → **`1553 Cannot drop index 'X': needed in a foreign key constraint`** — drop the FK first, in its OWN statement; (b) `DROP FOREIGN KEY x` + `ADD CONSTRAINT x` in the SAME ALTER → **`1826 Duplicate foreign key constraint name 'X'`** — split into two statements; (c) to rename an index use **`ALTER TABLE t RENAME INDEX old TO new`** — it works on FK-backing indexes (MariaDB ≥ 10.5.2, MySQL ≥ 5.7), the FK follows the rename and stays enforced (verified). Note `DROP INDEX` on a name that simply does not exist reports the misleading **`1091 Can't DROP 'X'; check that column/key exists`** — check the name in `information_schema.statistics` before blaming the FK.
- **A schema-drift gate needs a reference DB and a NEGATIVE test.** Build `kanpad_rs_ref` from the same migrations (`DB_NAME=kanpad_rs_ref cargo run migrate run` — the env var overrides `.env` because dotenvy never overrides an existing var) and compare indexes + constraints against the staging DB **in both directions** (column/index ORDER differs legitimately between two builds, so compare semantics, not raw `SHOW CREATE TABLE` text). Always **inject a deliberate drift** (e.g. `ALTER TABLE cards ADD INDEX IDX_DRIFT_PROBE (title)`) to prove the gate is not vacuously green, then remove it. The gate is trivially green right after `migrate run`; its value is after any hand-written `ALTER`, and against the PROMOTED prod DB before unfreezing writers.
- **The scratch DB is a reference, not a loss-prevention step.** Restoring the same file into utf8mb4 loses nothing (identical text) — the latin1 scratch earns its keep because it is the byte-exact prod replica the fidelity gates compare against. Keep the runbook's shape: one dump → one scratch restore → one cross-DB import → gates → seed → blue-green promote.

### Code review + quality baseline (2026-10-22, `backend-rs/`)

A review of `backend-rs/` (organization, architecture, idiomatic Rust, industry best practices) produced a 10-axis scorecard and a 9-task program (`specs/api-rewrite-rs-specs/54-rust-idiom-hardening.md` + `50-tasks.md` Phase 7, T54–T62) to lift every axis to ≥ 9.5/10. Lessons:

- **A gate that has never executed is not a gate.** `backend-rs/.github/workflows/ci.yml` sat one directory deep — GitHub discovers workflows ONLY at the repo root's `.github/workflows/` — so the pipeline had **never run**. Replaying its grep gate by hand immediately failed on three `expect` sites. A perfect gate definition is worth less than a green run: **validate every gate by making it go red on purpose**, and check the workflow's LOCATION, not just its content.
- **A hand-maintained allowlist drifts — assert it with a test.** `CorsLayer::allow_methods` omitted `PUT`, so `PUT /cards/{id}/labels/{label_id}` was blocked by the browser preflight while every other verb worked (the frontend calls it; compose sets `VITE_API_URL`, making the call cross-origin). The fix is the method list AND a preflight test that asserts every served verb survives — axum does not expose the route table, so the test is the guard. **Landed in T55.**
- **A test that asserts the MECHANISM is not a test of the POLICY.** The pre-existing `health::cors_preflight_matrix` checked ACAO + credentials for **POST only** — correct, green, and blind to the `PUT` drift. The new guard enumerates **every served verb**. A policy test must cover the policy's *domain*, not one sample of it.
- **A gate that has never executed fails on false positives first.** The `no format! in store.rs` gate had never run either, and it failed on the current tree for two reasons that were the GATE's fault: a doc comment merely mentioning `format!`, and `notes::escape_like_pattern` building a **bound value** (the sanctioned LIKE pattern) rather than SQL. **When a gate's intent is right but its matcher is wrong, fix the GATE — and never "fix" the code to satisfy a matcher that misreads the intent.** The gate now skips comments and flags a `format!` only when the built text carries a SQL keyword.
- **A guard that lands red is not a guard.** The CORS preflight guard could not be green until `PUT` was in `allow_methods`, so the fix moved from T56 into T55 (with the guard) rather than landing a red suite in the freshly-activated CI.
- **`#[tracing::instrument(skip(state))]` records the request body.** `skip` takes *only* what it names; every other argument is recorded via its `Debug` impl — so `auth.email` and the DTO body (card `title`/`description`) landed in the span. Skip the body + session explicitly, and gate it with a grep.
- **Make a compile-time fact a compile-time fact.** `to_response(Vec::from([row]), …).pop().expect(…)` asserted a cardinality the compiler already knew. Give the store a single-row constructor (`to_response_one`) so the invariant is structural. **Landed in T55** — `columns/store.rs::to_response_one` + the create/update call sites.
- **A rename must not fail open.** `APP_ENV` defaults to `development`; if `NODE_ENV` were merely ignored, a stale deployment would silently drop `Secure` cookies + `__Host-` + HSTS + deny-all CORS. Boot **fails** when `NODE_ENV` is present — **landed in T54** (`ConfigError::LegacyNodeEnv`, checked *before* `envy` reads `APP_ENV`). Same discipline as the DB-name screen, the charset requirement, the `HASH_COST` prod floor.
- **`common/` is the shared kernel — "features never import each other's STORES" is a SQL-ownership rule, not a ban on sharing a formatter.** `format_timestamp` was duplicated 9× and `common/ownership.rs` was an empty stub while the ownership SQL was duplicated across features. Both belong in `common/`.
- **The rewrite's own constitution is a checklist.** `00-overview.md` says "no NestJS-isms are carried over" — yet `NODE_ENV` and `connect.sid` (express-session's default, copied from `backend/src/main.ts`) survived. Audit the *names* against the constitution, not just the shapes.
- **A lint gate must not flag the fix the same task prescribes (2026-10-22 (c)).** B2's new grep gate was drafted to match `panic!`/`unwrap_or_else`/`todo!`/`unimplemented!` — but `unwrap_or_else` is used **benignly 6×** (it is not a panic spelling) and `state.rs`'s documented fail-fast **is** `unwrap_or_else(|_| panic!(…))`, i.e. the exact line B2 told the executor to write. The gate now matches `panic!`/`todo!`/`unimplemented!` with the ONE boot-time fail-fast explicitly allow-listed. **Rule: before adding a grep gate, grep the tree for the pattern you are about to forbid — and prove the gate goes RED on a probe.**
- **Measure a lint's debt before you make it a gate (2026-10-22 (c)).** `clippy::pedantic` was assumed clean; measured, it is **~370 warnings** (173 `missing_errors_doc`, 45 `must_use_candidate`, 22 `doc_markdown`, ~40 `cast_*`). With CI's `-D warnings` it would have turned a build task into a 370-warning refactor whose `cast_*` fixes change runtime semantics. By contrast `missing_docs`/`unreachable_pub` measured **0** — the deny-level `missing_docs` gate is free. **A lint you have never run is a lint of unknown size.**
- **Two gates over the same subject with different policies guarantee one is red (2026-10-22 (e)).** The workflow ran `cargo audit` AND `cargo deny check advisories` — but `cargo-audit` reads `.cargo/audit.toml` (absent) and `cargo-deny` reads `deny.toml` (4 task-bound ignores). The audit step failed on exactly the advisories the project had deliberately accepted (`error: 4 vulnerabilities found!`). **One policy, one gate, one source of truth** — a second ignore list can only drift.
- **A pipeline that has never run is not a pipeline (2026-10-22 (e)).** T55 moved the workflow to the repo root, which made it discoverable — and therefore verifiable — for the first time. Replaying every step by hand found **two steps RED on every run** (the audit conflict; a SHOW CREATE TABLE assert querying the pre-2026-10-19 `tower_sessions` schema, which the app-database store change had made non-existent). Both had been broken since the day they were written. **Replay EVERY step, not just the ones you changed** — and a step whose assertion describes a schema/table that a *previous* task moved is a step that has been lying since that task.
- **A config file's format belongs to a pinned tool version (2026-10-22 (e)).** `cargo-deny` was installed unpinned; the first run of the T57 policy failed with `unexpected-keys … deny-multiple-versions` because the file was written against a wrong schema. A `deny.toml` is schema-version-sensitive exactly like a `.sqlx/` cache is driver-version-sensitive: **pin the tool** (`--version 0.20.2`) so a tool release cannot turn a dependency bump red.
- **A plan that is EXECUTED drifts from the plan that was READ (2026-10-22 (e)).** Five tasks landed between writing `54` and reviewing it, and in that time the spec had drifted in **both** directions: it still described a tree that no longer existed (`NODE_ENV`, `connect.sid`, the undiscoverable workflow, a failing lint gate, a missing `PUT`) **and** it described a tree that never existed (T65's "five store files" — there are **eight**; "no task touches `openapi.json`" — T57 did). **Re-verify the plan's claims against the tree after every task lands** — and check the plan's *file lists* and *counts*, not just its decisions: a count that is wrong by three makes a task's own acceptance criterion fail.
- **A transitive FEATURE can vanish with the crate that enabled it (2026-10-22 (f)).** The session sweeper's loop (`ExpiredDeletion::continuously_delete_expired`) lives behind `tower-sessions-core`'s `deletion-task` feature — which `tower-sessions-sqlx-store` enabled **transitively**. Dropping the store dropped the feature, and `main.rs` stopped compiling with a method that no longer existed. **When you remove a dependency, enumerate what it enabled transitively**: features, macro exports, and provided trait methods. The fix was to declare `tower-sessions-core` directly with the feature (the SAME version the middleware pins — so no second core in the tree).
- **A dependency's removal can make an invariant STRUCTURAL (2026-10-22 (f)).** The old session store interpolated a **schema name** into every statement, so "the store must live in the pool's database" had to be *configured* (a name, validated at boot, with a `panic!` when it was not a valid identifier). The in-tree store takes the pool and interpolates **nothing** — the same invariant now holds by construction, so the validation, the panic, its `# Panics` contract, and the CI grep gate's allow-list entry for it all became obsolete. **When a gate's allow-list entry loses its subject, delete the entry** — an allow-list entry that outlives its reason is a hole.
- **A toolchain pin CI ignores is not a pin (2026-10-22 (c)).** `dtolnay/rust-toolchain@stable` exports `RUSTUP_TOOLCHAIN`, which **overrides `rust-toolchain.toml`** — so the file can pin 1.99.1 while CI still floats on `stable`. Check the *precedence*, not just the file's existence.
- **Edition 2024 makes `std::env::set_var`/`remove_var` UNSAFE — a test harness that mutates the process env is a blocker, not a detail (2026-10-22 (d)).** The config tests drove `Settings::load_from_env()` by mutating the process env; edition 2024 + `unsafe_code = "forbid"` makes that impossible. The fix is a **seam, not an `unsafe` block**: `Settings::from_pairs(&[(k, v)])` loads from an explicit map (same deserialize + validate path, different source). The tests then need neither `unsafe` nor the `ENV_LOCK` mutex — and become parallel-safe. **When a language edition changes a safety rule, re-check every place that relied on the old rule — the compiler tells you, but only after you try.**
- **A dependency refresh is a security fix — review the lock diff for DOWNGRADES, not just for changes (2026-10-22 (d)).** `cargo deny check advisories` found 6 real advisories; the fix was a `cargo update` that moved **25 crates upward** (incl. `rustls 0.23.45 → 0.23.46`). The review question is "did anything get WORSE?", not "did anything change?".
- **A dead direct dependency can carry a whole second framework (2026-10-22 (d)).** `axum-valid 0.20` had **zero** references in `src/` — and dragged a complete second **axum 0.7.9** (axum-core 0.4.5, matchit 0.7.3), the `validator` 0.18 framework (via `axum-valid`'s DEFAULT features) and a second `garde` 0.20 into the tree beside the real axum 0.8.9. `cargo clippy` never reports an unused *direct* dependency and `cargo build` never reports a duplicate one. **Grep every direct dep against `src/`+`tests/` with a qualified-path pattern** (`tower_http` ≠ `tower`, `std::time` ≠ the `time` crate — that false positive flagged `time` as dead, and it is REQUIRED by `tower_sessions::Expiry`).
- **Bind every supply-chain ignore to a task that removes it (2026-10-22 (d)).** All 6 advisories were removable by later tasks in the same phase (T63/T66/T67). Each `deny.toml` ignore records the advisory id, WHY it is acceptable now, and the exact task that must delete it — an unbound ignore is a silent hole in the gate.

### Rust backend (`backend-rs`)

- The session store follows the POOL's database: `AppState::with_pool(settings, pool)` binds `MySqlStore` to `pool.connect_options().get_database()` (`.with_table_name("sessions")`). `#[sqlx::test]` builds its pool with `.database(&db_name)`, so the per-test DB name is already in the connect options — no `SELECT DATABASE()` round-trip and no hand-wired store in tests. Production boots through `AppState::from_settings`.
- `MySqlStore::with_schema_name` validates identifiers STRICTER than MySQL (rejects a leading digit, `-`, `.`, space). `Settings::validate` screens the DB name via `db::is_valid_db_name` so a bad `DB_NAME` is a clean `ConfigError` — never a boot panic when the store is constructed. `DATABASE_URL` and `DB_NAME` are two spellings of the same value; validate whichever is in play.
- `dotenvy::dotenv()` never OVERRIDES an existing env var — it only ADDS missing ones. So a developer's local `.env` silently re-supplies a key a test deliberately unset, and a "this must fail to boot" assertion passes for the wrong reason. `Settings::load_from_env()` (no dotenv) exists for exactly this; the config unit tests use it, boot uses `Settings::load()`.
- Rust test helpers: in-process suites own their plumbing in `backend-rs/tests/api/helpers.rs`; black-box (raw TCP) suites share `backend-rs/tests/api/wire.rs`. Import EXPLICITLY (`use super::helpers::{…}`) — a glob import lets a leftover local copy silently win, while an explicit import is a hard `E0255`. That compile error is the regression guard for "no per-suite helper copies".
- The two black-box suites and the in-process suites assert problem+json through ONE core (`helpers::assert_problem_fields`); the transport-specific `assert_problem` functions are thin adapters. Keep new problem assertions in the core.
- `backend-rs/tests/api.rs` needs an explicit `#[path = "api/<name>.rs"] mod <name>;` for every suite — a bare `mod health;` resolves to `tests/health.rs`, which does not exist.
- `cargo fmt --check | tail` MASKS the exit code (the pipeline's status is `tail`'s). Capture `$?` without a pipe (`> file; echo $?`).
- A test that binds a FIXED port (e.g. `TcpListener::bind(":3001")`) breaks under cargo's parallel test scheduler when two suites in the same binary pick the same port — and also breaks if a dev server already holds that port. Bind port **0** (OS-assigned ephemeral) and drive `listener.local_addr()`; the OS may hand out a different port than requested, so never re-derive the address from the requested port. `wire::bind_blackbox()` in `backend-rs/tests/api/wire.rs` does this for both black-box suites; `E2E_BASE_URL` pins a fixed port when an operator needs one.
- A normative ownership header that the CODE VIOLATES is worse than no header — a future contributor trusts it and copies the pattern. The E0255 guard only fires for names a suite actually IMPORTS, so a suite can shadow a shared name forever just by not importing it (`auth_register.rs` aliased `json_of as parse_json` to dodge the collision; `throttle.rs` imported nothing from `super::helpers` at all and kept its own `send` + a duplicate `PROBLEMS` const). Audit the forbidden set against the actual `fn` definitions, not against the import statements — and when a suite legitimately needs its own helper, it must take a name OUTSIDE the forbidden set AND be listed in the header's "Sanctioned exceptions".
- When auditing a forbidden set, grep for the DEFINITIONS, not the imports — and make sure the pattern covers EVERY name in the set. A first audit of the session-store change missed `health.rs`/`errors.rs` shadowing `test_settings`/`test_app` and three suites duplicating the `PROBLEM_BASE` literal, purely because the grep pattern had omitted those names. Grep the whole forbidden set, then re-grep for the constant's VALUE (`https://kanpad.dev/problems`) to catch inline duplicates of a "constant" that were never imported.
